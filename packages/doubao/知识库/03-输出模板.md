# 输出模板

收尾时读本文件。产出两个文件，写入 `prototypes/<原型名>/`（目录不存在则新建；不要碰
`index.html` / `style.css` / `script.js` —— 那是开发阶段的事）。

---

## 一、DESIGN_SPEC.md

设计规格书。这是**需求审计链的源头** —— 开发阶段会把它转写进
`REQUIREMENTS.md`，所以它必须能独立读通：不要写"如上所述"、"见前面"。

```markdown
# <原型名> — 设计规格

> 生成日期：YYYY-MM-DD | 引导轮次：R1–R3 | 设计版本：v1

## 0. 一句话定位

<一句话说清这个工具是什么、给谁、在哪一刻用>

<现在怎么做的；现有载体（Excel/系统/白板）里可直接搬过来的字段和流程>
- 现状载体：<例：一个 Excel，表头 A/B/C/D>
- 最烦的环节：<例：每次要手工比对两边的编号>

<哪件事变快或消失了，就说明它有用>
```

```
| | | <用户确认 / 默认值> | |
```

**填写要求**

- 每一节都要有值。用户没答的，填默认值并记进第 5 节 —— 留空比填默认值危险得多，留空会
  让开发阶段重新问一遍，等于访谈白做。
- 第 3.4 节不能是空的。"这次全都要做"是极少数情况；若真如此，写明"无，本轮全量"。
- 表头的字段名用用户的原话，不要"标准化"成你以为更专业的词。用户说"料号"就写"料号"。

## 二、PROMPT.md

可直接投喂的提示词。用户要的是「一套」，所以给一条主提示词 + 可选的分段提示词。

**取舍**：原型不大就用主提示词一条走完（分段反而增加往返）。功能分区多、字段表长、
或者用户明显会分几次做时，才给分段版。

```markdown
# <原型名> — 开发提示词

## 主提示词

新建原型 `<原型名>`。

**定位**：<一句话定位>

**布局**：<整图模式>。<主区形态>。结构：
```
<ASCII 草图>
```

**主区字段**：<字段名（类型）>，共 N 个。其中 <字段> 可搜索，<字段> 可筛选，<字段> 可排序。
枚举取值：<字段> = A / B / C。

**核心交互**：<动作 1>、<动作 2>、<动作 3>。
**状态与分支**：<需要的状态清单>。
**不需要**：<明确不做的清单>。
**视觉基调**：<基调>。
**模拟数据**：<数据项> 各 N 条，覆盖 <边界情况>。

技术约定遵循 `04-技术规范.md`。

## 分段提示词（可选）

### 第 1 段 — 骨架与静态布局
按上面的布局和字段表，搭出 HTML 骨架 + CSS 主题 + 静态渲染。
数据用 `MOCK_DATA` 常量，先写死。不接任何交互。

### 第 2 段 — 主功能
实现 <动作 1>、<动作 2>、<动作 3>。

### 第 3 段 — 状态与分支
补齐 <状态清单>：空态、加载、错误、二次确认……

### 第 4 段 — 视觉打磨
按 <基调> 调整视觉细节，调用 `ui-ux-pro-max` 审查。
```

**填写要求**

- 提示词里**不要**出现 `DESIGN_SPEC.md`、`REQUIREMENTS.md`、"参考设计规格"、"见前文"、
  "配套文档" 等任何指代 —— 包括标题下那行引用也算。提示词要能脱离 `DESIGN_SPEC.md`
  独立成立，因为实际使用时它可能被单独复制到新会话里。需要溯源时，把"本文档由
  `DESIGN_SPEC.md` 派生"写在 DESIGN_SPEC 一侧，不写在 PROMPT 里。
  自检：把 `PROMPT.md` 全文粘到一个空会话里，里面每一句话都必须成立。
- 字段名、枚举取值、状态清单全都写全，不要用"若干"、"等"。
- 技术约定只写"遵循 `04-技术规范.md`"一句，不要复述 CSS 变量、JS 规范 ——
  那是执行层的规则，在这里重复会和它打架。

## 三、交接

两个文件写完后，做最后一次整体回声确认，然后进入开发阶段（见 `01-完整规则.md` 第二部分）：

1. 把 `DESIGN_SPEC.md` 作为需求来源，需求澄清已完成，不再重复提问。
2. 复制 `原型模板/` 到 `prototypes/<原型名>/`，写 `REQUIREMENTS.md`、编码、
   维护 `CODE_ARCHITECTURE.md`。
3. 提醒用户：产出是可直接双击打开的静态文件。

不要在访谈阶段执行编码、复制模板、Git 操作 —— 职责分界。两套规则重复会互相打架。
